## 1. Needs fixing — things I introduced that are wrong

### 1.1 `recents.json` grows without bound  ⚠️ HIGHEST
`POST /api/recents` writes one row per **scope**, and guests are scoped by
session id. Every guest session that plays a track creates a permanent row that
nothing ever prunes. Prod already has **6 `sid` rows from test sessions alone**
after a few hours:

```
rows: 8   by scope: {'sid': 6, 'actor': 2}
```

On a public site this is unbounded file growth, and the whole file is read and
rewritten on every play. **Fix:** TTL or cap the `sid` rows (drop anything not
updated in ~30 days, or keep the newest N), or don't persist guest recents at
all and leave them in `localStorage`. Actor rows are fine — bounded by users.
Introduced by me today; the library/playlists stores have the same shape but are
write-on-user-action, not write-on-every-play.

### 1.2 Spend over-credits by one tick at the balance floor
Long-standing, flagged early, never fixed. When a balance hits zero mid-tick the
full tick is still added to `spend` while the balance clamps at 0 — observed
`spend 0.00083` against a balance of `0.0006`. Harmless while payments are
simulated; **must be fixed before real money.** `server.js`, the
`if (played > 0 && isPaymentEligible(song))` block in `tick()`.

## 3. Known-incomplete by design (not bugs, but don't mistake them for done)

- **`payments_enabled: false`.** Listener balances are mock seeds. The *payout*
  leg is proven on testnet (real tx `5008aa41419fc5c1c98b5fb54c1f2aac2ecaab03e253550672c47245117f1eab`,
  ondastream → musictesting, 0.0031 XPR) but **no real money goes in.**
- **Settlement is a manual script**, `app/settle_payout.mjs`. Deliberately not a
  server endpoint — settling needs a signing key and the web server must never
  hold one. Production wants a treasury signing on a schedule, or the on-chain
  recorder pattern.
- **`chapeldeep` is not a chain account.** Artist rows are display-only; payouts
  are pointed at `musictesting` because it was the spare funded wallet.
- **`xprmusic` cannot pay anything** — zero staked NET/CPU (`net 0/0`), fails with
  *"transaction net usage is too high"*. Use `ondastream` as treasury.
- **Chapel Deep tracks are filed under "Electronic"** — there is no House
  category. Adding a 7th genre is one line in `CATEGORIES`.

## 4. Traps for whoever deploys next

### 4.1 `catalog/*.json` on prod is LIVE USER STATE — merge, never overwrite
This nearly bit me today. Prod had an album **"hey hey"** and an edited
`xprmusic` bio that local did not. A normal push would have deleted both
**silently** — same "uploaded, checksums match" output as a good deploy.
(Gabriel later asked for "hey hey" to be removed, and it was — via
`DELETE /api/albums/:id`, not by hand-editing. The point stands: it should be
deleted on purpose, not as a deploy side-effect. His "Debut EP" is still there.)

- **Code** (`server.js`, `desktop.html`, `mobile.html`): local is newer, overwrite is correct.
- **Catalog** (`songs/albums/artists/playlists/balances/recents`): the site writes these. Diff and merge.

### 4.2 `server.js` changes need `systemctl restart xpr-music`
Which drops every in-flight listening session. Static-only pushes do not.

### 4.3 Recents overwrite forward on first sync
A device's existing local history is replaced by the account's server list, not
merged. Deliberate, but surprising if a phone had history the desktop never saw.
